# System Requirements

Требования к системе бронирования переговорок + сервис уведомлений.

Числа из ТЗ взяты как данность, остальные выведены из них.

## Нагрузка

### Booking-service

| Метрика | Значение |
|---------|---------|
| Суммарный RPS | 100 |
| Read / Write соотношение | 80 / 20 |
| Пиковых записей (create/cancel booking) | ~20 RPS |
| Самый нагруженный эндпоинт | `GET /rooms/{roomId}/slots/list` |

### Notification pipeline

| Метрика | Значение | Обоснование |
|---------|---------|------------|
| Событий в Kafka (пик) | ~20 событий/сек | ≤ write RPS booking-service |
| Событий в Kafka (средн.) | ~5 событий/сек | 100k броней / рабочий год |
| Kafka partitions | 1 | запас 50x от нагрузки, один partition ≈ 1M msg/sec |
| Concurrent SSE-соединений | ~500 | 10k пользователей → 10% онлайн → 50% с открытым браузером |

## SLA / SLI

| Метрика | Значение | Источник |
|---------|---------|---------|
| Availability booking-service | 99.9% | ТЗ |
| Availability notification-service | 99.5% | некритичный путь |
| Latency `GET /slots` p95 | < 200ms | ТЗ |
| Latency остальных эндпоинтов p95 | < 500ms | выводится |
| Delivery latency уведомления p95 | < 1s | booking-событие → SSE в браузере |
| Допустимый lag Kafka consumer | < 30s | задержка уведомления некритична |

## Гарантии доставки

**At-least-once** — выбранная стратегия.

Обоснование:
- Outbox pattern: событие пишется в `outbox` в той же транзакции что и бронь → потеря исключена
- Kafka consumer вручную commit-ит offset после сохранения в БД → при рестарте обрабатывает повторно
- Таблица `notifications` имеет `UNIQUE (booking_id, event_type)` → дубли идемпотентно игнорируются через `ON CONFLICT DO NOTHING`

Exactly-once — избыточно: получить дубль «Ваша бронь создана» некритично.

## Fault tolerance

| Сценарий | Поведение |
|---------|---------|
| Kafka недоступна | бронь создаётся ✅; outbox накапливает события; relay публикует после восстановления |
| notification-service упал | сообщения хранятся в Kafka (retention 7 дней), обрабатываются после рестарта |
| SSE-соединение разорвалось | клиент переподключается; пропущенные уведомления читает через `GET /notifications?unread=true` |
| БД booking-service недоступна | outbox и бронь не пишутся вместе → транзакционная консистентность гарантирована |

## Хранение уведомлений

| Параметр | Значение |
|---------|---------|
| Retention | 90 дней |
| Расчётный объём | 10k users × 10 событий/день × 90 дней ≈ 9M строк ≈ 2GB |
| Стратегия очистки | партиционирование по дате или background job удаления |
