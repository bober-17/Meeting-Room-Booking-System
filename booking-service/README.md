# booking-service

Сервис управления переговорками и бронями. Администраторы создают переговорки и настраивают расписание доступности — дни недели и временной диапазон. На основе расписания система автоматически формирует 30-минутные слоты. Сотрудники просматривают свободные слоты и бронируют их; при создании брони опционально генерируется ссылка на видеоконференцию. Один слот — одна активная бронь.

Сервис доступен на `http://localhost:8080`.

## Аутентификация

Все эндпоинты, кроме `/_info`, `/dummyLogin`, `/register`, `/login`, требуют JWT:

```
Authorization: Bearer <токен>
```

```bash
# Токен администратора
curl -s -X POST http://localhost:8080/dummyLogin \
  -H "Content-Type: application/json" \
  -d '{"role": "admin"}'

# Токен пользователя
curl -s -X POST http://localhost:8080/dummyLogin \
  -H "Content-Type: application/json" \
  -d '{"role": "user"}'
```

Время жизни токена — 24 часа.

## Типичный сценарий

**Шаг 1. Получить токен**

```bash
curl -X POST http://localhost:8080/dummyLogin \
  -H "Content-Type: application/json" \
  -d '{"role":"user"}'
```

**Шаг 2. Получить свободные слоты**

```bash
curl "http://localhost:8080/rooms/10000000-0000-0000-0000-000000000002/slots/list?date=YYYY-MM-DD" \
  -H "Authorization: Bearer <TOKEN>"
```

**Шаг 3. Создать бронь**

```bash
curl -X POST http://localhost:8080/bookings/create \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"slotId":"<SLOT_ID>","createConferenceLink":true}'
```

**Шаг 4. Отменить бронь**

```bash
curl -X POST http://localhost:8080/bookings/<BOOKING_ID>/cancel \
  -H "Authorization: Bearer <TOKEN>"
```

```

    ↓
```

## Ключевые архитектурные решения

**Ленивая генерация слотов** — слоты создаются при первом запросе `GET /slots/list`, а не заранее. Вставка идемпотентна через `ON CONFLICT DO NOTHING`. Альтернатива (cron-генерация) требует фонового процесса — дополнительная точка отказа без реальной пользы при нагрузке на ближайшие 7 дней.

**Защита от race condition при бронировании** — частичный уникальный индекс `WHERE status = 'active'` на таблице `bookings`. При конкурентной вставке одна транзакция получает SQLSTATE 23505 → HTTP 409. `SELECT FOR UPDATE` не используется — уникальный индекс обеспечивает оптимистичную блокировку без снижения пропускной способности.

**Атомарная отмена + идемпотентность** — отмена реализована одним запросом без явной транзакции:
```sql
UPDATE bookings SET status = 'cancelled'
WHERE id = $1 AND status = 'active' AND user_id = $2
RETURNING ...
```
При 0 строк выполняется диагностический `SELECT`: бронь не найдена или принадлежит другому пользователю → 404 (намеренно: не раскрываем существование чужой брони), уже отменена → 200. Проверка владельца встроена в `WHERE` атомарно.

**`/bookings/my`** — возвращает только брони со статусом `active` и `start_at >= now()`. Отменённые и прошедшие брони не включаются.

**`/rooms/list` без пагинации** — список переговорок возвращается целиком. ТЗ явно ограничивает объём до 50 записей — пагинация избыточна и усложняет клиентский код без реальной пользы. `/bookings/list` пагинирован, потому что ТЗ требует этого явно и объём до 100k записей.

**Outbox pattern** — события `booking.created` / `booking.cancelled` записываются в таблицу `outbox` в той же транзакции что и бронь. Фоновый relay публикует их в Kafka через `FOR UPDATE SKIP LOCKED`.

**Сбой конференц-сервиса** — бронь сохраняется без ссылки, не откатывается. Откатывать успешную бронь из-за сбоя внешнего сервиса значит поставить доступность нашего сервиса в зависимость от стороннего.

**dummyLogin-пользователи** — `admin` и `user` создаются seed-миграцией с фиксированными UUID (`...000001`, `...000002`) и `password = NULL`. Фиксированные UUID нужны, чтобы `user_id` в JWT ссылался на реальную запись в таблице `users` (внешний ключ в `bookings`). Из-за `password = NULL` эти пользователи не могут войти через `/login` — только через `/dummyLogin`.

**Защита от timing oracle в `/login`** — при ненайденном email `Login` всё равно вызывает `bcrypt.CompareHashAndPassword` против заранее вычисленного sentinel-хеша, чтобы время ответа не зависело от того, существует ли email. Без этого атакующий различает «email не найден» (~1 мс) и «неверный пароль» (~100 мс) и перебирает адреса по задержке.

**`roomId` при создании расписания** — если `roomId` передан и в path, и в теле запроса, используется значение из path. Тело не валидируется на совпадение. Path-параметр однозначно идентифицирует ресурс; значение в теле — избыточно.

**Настройки пула соединений** — `maxConns = 20`, `minConns = 2`, `maxConnLifetime = 1h`, `maxConnIdleTime = 30m`, `connectTimeout = 5s` захардкожены в коде, не выносятся в env. Это технические ограничения приложения, а не конфигурация среды; менять их имеет смысл только вместе с изменением кода после нагрузочного тестирования.

**Рост таблицы `slots`** — таблица растёт бесконечно (~1k слотов/день × 50 комнат). Прошлые слоты не нужны: `/bookings/my` фильтрует по `start_at >= now()`. Очистка не реализована в рамках задания. Стратегия для production:
```sql
DELETE FROM bookings WHERE slot_id IN (
    SELECT id FROM slots WHERE end_at < NOW() - INTERVAL '30 days'
);
DELETE FROM slots WHERE end_at < NOW() - INTERVAL '30 days';
```
Порядок удаления важен из-за FK; альтернатива — `ON DELETE CASCADE` на `bookings.slot_id`.

**Валидации сверх ТЗ**

| Поле | Правило | Обоснование |
|------|---------|-------------|
| `daysOfWeek` | нет дубликатов | дубликаты — ошибка клиента; молча дедуплицировать значит скрывать её |
| `startTime` / `endTime` | минуты кратны 30 (00 или 30) | иначе слоты начинались бы в нестандартное время |
| `endTime` | строго позже `startTime` минимум на 30 мин | диапазон меньше одного слота делает расписание бесполезным |
| `password` | не более 72 байт | bcrypt молча обрезает на 72 байтах — два разных пароля могут дать одинаковый хеш |
| `email` | `net/mail.ParseAddress` | отсекает явно некорректные адреса; строгая RFC-валидация избыточна, уникальность гарантирует БД |
